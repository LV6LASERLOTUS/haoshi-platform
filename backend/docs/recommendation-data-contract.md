# 組織資料與假資料規格 v0.2

依使用者提供的「好事大平台：分場 A・資料流程 × AI 自動化」圖片修正。
以組織為中心，所有業務資料用 `organization_id`（組織編號）串接。
來源欄位與假資料以此文件為準，第一版規則與 BGE 整合方式另見
[推薦流程](recommendation-pipeline.md)；權重尚未依真實案例調整。

## 資料檔案與規模

- [recommendation-example.json](recommendation-example.json)：目前使用的 v0.2 假資料。
- 組織主檔：48 家，一家一列。
- 接觸紀錄：200 筆，一次接觸一列。
- 顧問筆記：20 筆，涵蓋 14 家組織。圖片寫「14 家有」，不是限定 14 筆。
- 任務卡：2 張情境卡；圖片是「二選一」，兩張作為範例，不表示必須同時實作。
- [舊規格](recommendation-data-contract-v0.1.md) 與 [舊範例](recommendation-example-v0.1.json) 保留供既有轉接測試使用。

全部名稱、類別值、日期、敘述與來源都是虛構，沒有引用真實個資或真實組織評價。
財報類型、會籍、陪跑分級的選項只是示範，待正式欄位說明確認後再建立代碼表。

## 圖片欄位對照

### 組織主檔 `organizations`

| 圖片欄位 | JSON 欄位 | 範例 / 說明 |
| --- | --- | --- |
| 組織編號（所有分頁串接） | `organization_id` | `ORG-001`，穩定識別碼 |
| 組織（一家一列） | `name` | 示範童學北區協會（虛構）；補上的顯示欄位 |
| 議題 | `issue_tags` | `["兒童教育", "數位學習"]` |
| 服務對象 | `target_groups` | `["兒童", "青少年"]` |
| 區域 | `regions` | `["臺北市"]`；保留來源層級，暫不推論是據點或服務範圍 |
| 會籍 | `membership_status` | 示範：有效會員、待續會、非會員、未知；實際含義待確認 |
| 全職人數 | `full_time_staff_count` | 非負整數；0 與未知不同 |
| 財報類型 | `financial_report_type` | 原樣保留示範類別，不轉成財務好壞 |
| 財報類型右側「…上架」 | `platform_listing_status` | 原欄名與意思待確認，目前全部為 `null`，不猜測平台或用途 |
| 陪跑分級 | `support_tier` | 原樣保留示範標籤，不假設大小順序或推薦優先級 |

### 接觸紀錄 `contacts`

| 圖片欄位 | JSON 欄位 | 說明 |
| --- | --- | --- |
| 組織編號 | `organization_id` | 必須指向主檔 |
| 日期 | `date` | `YYYY-MM-DD` |
| 接觸類型 | `contact_type` | 培力課程、課後追蹤、陪跑、走訪、會員大會、危機諮詢、獎補助入選 |
| 活動名稱 | `activity_name` | 不知道時為 `null` |
| 參與者職稱 | `participant_roles` | 多位參與者以清單保留；不填真人姓名 |
| 留下的話（自由文字） | `free_text` | 保留原始敘述，不預先標成正向或負向 |
| 資料來源 | `source` | 本範例用 `mock:` 前綴明示虛構來源 |

`contact_id` 是額外的技術識別碼，方便未來推薦理由引用特定紀錄。
類型只是來源分類，不能直接將危機諮詢當負評，或將獎補助入選當執行能力保證。

### 顧問筆記 `consultant_notes`

圖片描述有顧問與 PM 的觀察，但沒有列出實際欄名。以下是暫定結構，不宣稱來自正式表單：

| 暫定欄位 | 意義 |
| --- | --- |
| `note_id` | 筆記識別碼，供引用 |
| `organization_id` | 對應組織 |
| `recorded_on` | 觀察日期，未知就保留 `null`，不以匯入日期替代 |
| `author_role` | 資深顧問 / PM 等角色，不含真實姓名 |
| `note_text` | 原始觀察文字，包含保留意見與待確認事項 |
| `source` | 筆記、PM 工作紀錄、LINE 摘要等來源識別 |

主觀觀察與主檔事實分開存放；筆記不自動覆寫主檔，也不轉成固定能力分數。

### 任務卡 `task_cards`

使用 `task_id`、`title`、`scenario`、`user_role`、`questions`、
`requested_organization_count` 描述情境。這些是為了表達圖片任務新增的結構，
不是組織特徵，也不是預先產生的推薦結果。

1. 為一個計畫找對的組織：企業用專業陪跑 10 家組織，PM 提出名單與理由。
2. 讓散落的資料變成好用的入口：新 PM 接電話時，30 秒掌握一家組織。

## 缺漏、來源與檢查方式

- `null` 代表未知；0 代表明確的零；清單 `[]` 代表已知沒有列出項目。
- 6 家沒有接觸紀錄；只有 14 家有顧問筆記；也有僅有筆記、沒有接觸紀錄的組織。
- 部分主檔欄位、活動名稱、職稱、自由文字或筆記日期刻意缺漏。
- 有近期與較舊的紀錄，也有頻繁接觸的組織；資料量不等於品質或意願。
- `dataset_info` 是額外的資料集說明，包含假資料標記與固定基準日 `2026-11-12`。
- 主檔 `source` 是額外的追溯欄位；接觸紀錄 `source` 則對應圖片中的資料來源。
- 驗證基本型別、日期、ID 唯一性與跨表關聯；不限制真實資料必須有 48 家或 200 筆。
- 類別保留可讀中文，尚未定義正式標籤字典，不沿用 v0.1 的英文代碼要求。

在 `backend/` 執行：

```bash
python scripts/generate_mock_data.py
python -m recommendation docs/recommendation-example.json
```

生成器固定種子，重跑得到相同內容；預設更新上述假資料檔，也可用 `--output` 指定其他檔案。
這批資料用來確認欄位、串接與缺漏處理，敘述由有限的虛構模板組成，
不適合用來證明模型準確率。之後評估推薦效果時，另建需求案例與人工判斷的驗證集。

## 演算法留待資料確認後

先確認欄位含義、真實選項與缺漏方式，再依選定任務設計：

- 主檔提供議題、服務對象、區域與組織規模等條件。
- 接觸紀錄提供可追溯的活動、時間與需求敘述；不把接觸次數直接當能力。
- 顧問筆記提供有日期與來源的觀察；未知、過時與主觀意見應清楚標示。
- BGE 可作為查找相關文字的候選工具，不能據此宣稱合作成功率。

圖片沒有提供方案報價、承接容量、可合作檔期等資料，因此 v0.2 不建立這些欄位，
也不依它們篩選。之後取得真實資料再決定是否擴充。
